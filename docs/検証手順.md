# 検証手順 (BridgeProbe v2.0.0 + LiveContainer diag2.4)

必要なのは LiveContainer (diag2.4 以降) と BridgeProbe の 2 つだけ。AlarmClock も型紙も要らない。

## 準備

1. LiveContainer diag2.4 を SideStore で上書きインストール
2. このリポジトリを push → Actions「Build iOS IPA」→ `<時刻>_BridgeProbe-ipa` の ipa を **LiveContainer に**入れる
3. BridgeProbe を開き、AlarmKit の権限を許可する (初回の登録時に聞かれる)

## テスト

| # | スヌーズの方式 | 押すボタン | 成功の目安 (統合ログ) |
|---|---|---|---|
| 1 | どれでも | 停止 | `[Probe] ★ ProbeStopIntent が実行されました` |
| 2 | `.countdown` | スヌーズ | `★ ProbeSnoozeIntent … custom=false`。押してすぐ鳴り止むか、再鳴動の時刻を手でメモする |
| 3 | `.custom` | スヌーズ | `★ ProbeSnoozeIntent … custom=true` → `★ countdown(id:) 成功` で鳴り止む |

1. 「鳴るまで」の秒数とスヌーズの方式を選び「アラームを登録」
   - 直後に「包み替え N 件 (LiveContainer のメタデータから N 件)」と出れば、登録時の包み替えは成功
2. 画面をロックして待つ
3. 鳴ったらボタンを **1 回だけ**押す (連打しない)
4. BridgeProbe を開き「統合ログを開く」→ 右上の共有ボタン
   - 「直近のテスト以降」にすると、最後に登録した時刻からの分だけになる

`.custom` は Intent が走らないと鳴り止まない。止まらなければ停止ボタンで止める。

## 統合ログの読み方

| 印 | 書く人 | 主な行 |
|---|---|---|
| `[Probe]` | BridgeProbe | `登録` / `状態: A → B` / `★ …` |
| `[Bridge]` | LiveContainer の TweakLoader (このアプリのプロセス内) | `包み替え:` / `保留中の要求を実行します` / `実行完了 […] error=` |
| `[LC]` | LiveContainer 本体 | `呼び出し元: LiveActivityIntent` / `包み替えられた Intent:` / `LiveProcess 起動成功` |

段ごとの切り分け:

| 段 | 見る行 | 止まったときの意味 |
|---|---|---|
| 登録 | `[Bridge] 包み替え: LiveContainer のメタデータから組み立て` | 出ない → LiveContainer が diag2.4 でない / TweakLoader が読まれていない |
| 押下 | `[LC] 包み替えられた Intent: ProbeStopIntent` | 出ない → AlarmKit が包み替えた Intent を解決できなかった |
| 起動 | `[LC] LiveProcess 起動成功 pid=…` | `起動されず (pid=0)` → 前の子プロセスがまだ動いている (連打) |
| 実行 | `[Bridge] 実行完了 [A: metadata 付き] … error=(null)` | error の内容が次の手掛かり |
| 結果 | `[Probe] ★ …` | 実行完了なのに無い → perform まで届いていない |

`状態:` の行は BridgeProbe を画面に出している間だけ記録される (ロック中や画面なしの子プロセスでは記録されない)。鳴動中の状態を見たいときは、BridgeProbe を開いたまま鳴らす。

## 直インストールとの比較

同じ ipa を SideStore で直接入れると、Intent はこのアプリ自身で解決される (陽性対照)。
LiveContainer 内と結果を比べると、どこまでが LiveContainer 固有の問題かが分かる。
